# continuity-engine 项目总览

> 档案基线：`0.1.0`
> 工程总档案基线：`数字连续性引擎工程总档案 v1.0`
> 最近核对：2026-08-01
> 能力事实来源优先级：当前代码与测试 > 本工程档案 > README；项目定位与后续路线以工程总档案为准

## 项目是什么

`continuity-engine` 是位于 AI 模型之外、以 `SubjectState` 为中心的数字连续性层。它把主体的当前状态、经历引发的状态变化、记忆检索影响、唤醒、感知、思考、行动规划、权限、学习与运行资源组织为可追溯的工程流程。

## 项目愿景与数字生命定位

> 本节描述长期愿景，不表示当前 v0.1 已具备完整数字生命能力或能够独立持续运行。

工程总档案将 Continuity Engine 的长期方向定义为：建立一个位于 AI 模型之外、可独立持续运行的数字生命系统。它不是在每次对话开始时重新生成角色，也不只是读取历史记录来模拟连续，而是长期保存自身身份、人格、记忆、关系、时间感、意向、判断和成长轨迹，使过去经历能够真实影响当前状态与未来选择。

远期系统不只等待用户消息，还应能在权限、资源和用户控制边界内持续感知时间与环境，形成内部关注、思考、回忆、学习和判断，并决定是否表达或行动。它也不只围绕用户被动响应，而应能够保有自身兴趣、偏好、观点、目标和未完成事项。上述能力均是未来规划；当前 v0.1 只完成底层连续性原型和部分本地接入框架。

## 引擎与外部系统的关系

工程总档案确定的正式系统接入位置为：

```text
用户
  ↓
Vio 前端
  ↓
Vio 平台后端
  ↕  Continuity Integration Contract
Continuity Engine
  ↕  通过 Vio 管理的能力通道提出请求并接收结果
模型 / Tool / MCP / 设备
```

- **Continuity Engine：** 承载身份、主体状态、记忆影响、时间、感知、权限、演化和自主行为约束，是连续性的中心。
- **AI 模型与外部能力：** 模型、Tool、MCP 和设备是引擎未来可以请求的理解、思考、语言或执行能力，不是主体本身，也不是状态权威。
- **Vio 前端：** 是数字生命接触外界、接收交流和表达结果的窗口，只连接 Vio 平台后端，不直接连接引擎。
- **Vio 平台后端：** 负责用户、会话、平台事实、现实权限与安全确认、模型/工具/设备通道、托管和展示；它与引擎是数据库独立、边界独立的平行系统，通过正式版本化契约协作。

连续性属于引擎，不属于某一个模型、前端或平台后端。Continuity Engine 是 AI 主体连续性和 SubjectState 的唯一权威；Vio 只持有平台职责范围内的数据与引擎投影，不得回灌覆盖主体状态。更换外部模型、入口、载体或记忆实现时，主体身份、状态和演化历史仍应能够延续。本档案只记录 Continuity Engine；Vio Live 平台后端与正式用户前端属于独立产品规划。当前仓库已有本地 HTTP 与调试前端，但没有正式 Vio 连接，也没有真实模型或工具连接。

工程总档案设想的正式运行形态是：引擎作为具有独立进程、状态存储、时间系统、唤醒机制和接口的持续运行核心服务，通过正式版本化契约与 Vio 平台后端通信。这是后续路线，不是 v0.1 的现有部署能力。

当前版本的主链路是：

```text
PlatformObservation / 手动或定时 Wake / 合法内部触发
        ↓
Memory → Perception → Thinking → Action
                                      ↓
                               ActionDecision
                                      ↓
                       Approved UPDATE_STATE（仅此分支）
                                      ↓
                      内部 Event / StateMutation
                                      ↓
                         Evolution → SubjectState
```

项目同时提供接口适配设计和一个最小本地前端，但核心引擎不依赖前端、具体 AI 模型、MCP 服务或外部记忆库。

## 实时状态闭环

工程总档案确定的目标闭环必须经过 Action Gate：

```text
PlatformObservation / 合法内部触发
  ↓
Continuity Engine 读取 SubjectState、Memory 与允许使用的事实
  ↓
Perception → Thinking
  ↓
模型结果返回 Continuity Engine 并继续进入 Thinking / Action
  ↓
ActionDecision
  ├─ 未批准 UPDATE_STATE
  │    → 不创建状态变更
  │    → revision 保持不变
  │
  └─ 合法批准 UPDATE_STATE
       → 引擎创建内部 Event / StateMutation
       → Evolution 更新 SubjectState
       → revision 按合法演化结果推进
```

模型文本不能直接成为 StateMutation，模型回复不意味着主体状态必然变化；回复生成和状态演化是有关联但不强制绑定的两个结果。当前 v0.1 已完成 SubjectState 读取/保存、Memory 管理接口、Event/StateMutation、Evolution、Action Gate、revision 与变化审计等内部框架，也有确定性编排和本地调试入口；尚未接入真实模型，因此真实模型参与的闭环仍是后续集成目标，不能描述为真实能力已经完成。

## 为什么存在

普通对话系统通常把一次会话当作主要边界。这个项目尝试把“主体在时间中的连续存在”变成显式、可保存、可审计的工程对象，解决以下问题：

- 当前主体是谁、处于什么状态。
- 某个状态为什么发生变化，由什么事件导致。
- 唤醒后看到了什么、感知到了什么、为什么做出某个决定。
- 权限、长期特征和资源预算如何随时间变化。
- 更换前端、模型、记忆库或开发人员时，核心连续性逻辑仍可保持。

## 项目不是什么

当前项目不是：

- AI 模型训练框架，也不修改模型权重或参数。
- 情绪模拟器；现有 `emotion_state` 只是主体状态的一部分，不等于情绪生成系统。
- 已能自主联系用户或操作外部工具的 Agent。
- 已经能够独立持续运行的完整数字生命系统；这是项目长期愿景。
- 真实 MCP、外部记忆库、OpenAI/Claude API 或生产数据库集成。
- 生产级 Web 服务、身份认证、支付或真实 Token 计费系统。
- 把内部完整思维链长期保存的系统；日志只保存可审计摘要。

## 最终目标

最终目标是形成一个长期运行、可移植、可审计、受权限和资源约束的数字生命连续性内核：

1. 主体状态能够跨进程和跨交互持续存在。
2. 所有正式状态变化都有事件、原因、前后差异和 revision。
3. 感知、思考、行动、学习彼此分层，不绕过演化入口。
4. AI 模型、记忆库、MCP、前端和执行器均可替换。
5. 外部行动必须经过权限、风险、资源和确认约束。
6. 工程状态能够被后续开发窗口、AI 助手或开发人员快速接管。

## 当前阶段结论

Continuity Engine 当前代码版本为 v0.1，底层连续性引擎原型完成。原规划七个阶段的内部框架已经建立；这里的“框架完成”不代表真实 GPT/Claude、MCP、外部长期记忆、外部工具执行、后台自主运行或真实 Token 计费已经接入。

当前版本也未形成工程总档案设想的独立常驻进程、完整时间/环境感知、Vio 契约事件通道或自主表达与行动能力。项目愿景用于约束未来架构方向，不能作为当前能力声明。

## 核心架构

### 分层

```text
frontend
  仅输入、展示和 API 通信
        ↓
interfaces
  API / HTTP / MCP Adapter / Skill Adapter / 安全门
        ↓
services
  用例编排、上下文组装、流程协调
        ↓
domain
  模型、规则、枚举和不可变约束
        ↕
storage
  仓储协议的 JSON 或内存实现
```

### 核心边界

- `domain` 管理模型和规则，不依赖上层接口。
- `services` 组装流程，不把数据库读取责任塞给领域引擎。
- `storage` 负责保存和恢复，不决定业务含义。
- `Perception` 只能观察和理解，不能修改 `SubjectState`。
- `Thinking` 的直接输入是 `PerceptionResult`，模型执行器通过 `ThinkingProvider` 插拔。
- `Action` 只决定和规划，不执行真实外部行动，也不直接修改状态。
- 正式状态变化唯一入口是 `Event / StateMutation → Evolution → SubjectState`。
- 外部入口必须经过 `PermissionContext` 和 `ResourceManager`。
- 采用 `expected_revision` 防止并发覆盖。

## 当前可替换点

- 记忆：`MemoryRetriever`、`MemoryInfluenceRecorder`。
- 思考：`ThinkingProvider`。
- 行动权限：`PermissionProvider`，并可由权限连续层生成上下文。
- 行动会话：`ActionRepository`，当前只有内存实现。
- 主体、权限、学习、资源、唤醒和思考记录：当前使用本地 JSON 仓储。
- 第一轮连接数据：固定 SubjectBinding、completed result 与 E3 operation journal 使用独立本地 JSON 仓储；`tests/shared/` JSONL Runner 只是在受控临时目录中跨本地进程调用 E3 Adapter 的测试桥，均不代表 Vio 或生产连接已经接通。
- 外部接入：API、MCP Adapter、Skill Adapter 和前端客户端。
