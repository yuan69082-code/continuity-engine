# P11 队列、恢复、重试、取消与投递语义

## 1. 权威和边界

`SchedulerQueue` 是唯一 P11 调度权威，只保存任务身份与 subject/environment 绑定、priority、dueAt、wakeReason、顺序、revision、attempt、取消和回执摘要。它不是第二套 SubjectState、Event、Memory、Action 或 Capability Authority，也不保存任务正文和心理内容。

Scheduler 的输出是一次 computation opportunity。它不调用模型，不生成 thought/emotion/desire/will/decision/action intent，不运行 Planner/Action，不执行现实副作用。Engine 内组合测试把该机会交给既有 `ResourceAwareWakeScheduler → AwakeningService → WakeSession`；Wake 的既有决策仍只描述后续管线状态。

## 2. 身份与持久化

首次 `SchedulerService.submit()` 在任何仓储读取或写入前要求纯净初态：state 为 QUEUED，sequence/revision/attempt_count 全为 0，next_attempt_at、last_attempt_id、last_receipt_id/hash/status、cancel_requested_at、completed_at 全为 None，reason_codes 为 ()。任一不满足即抛出明确的 `SchedulerValidationError`，无队列写入、通知调用或资源副作用；伪造 attempt_count=max_attempts 的毒化任务无法入队。

此检查只属于 submit admission，不约束仓储加载/反序列化或既有记录恢复。调用方以原始纯净请求重复 submit 仍按身份返回既有记录；合法 RETRY_WAIT、UNKNOWN、COMPLETED 等历史状态继续通过原恢复链加载和处理。

- task identity 绑定 `taskId`、subject、environment、priority、dueAt、wakeReason、cycle/source Event、createdAt 和 maxAttempts。
- attempt identity 由 taskId 与单调 attempt number 确定性生成；崩溃重启后保持相同。
- receipt 必须精确绑定 task/attempt/subject/environment；普通同名字符串、错绑回执或缺失字段均不能证明投递结果。
- 单一 `scheduler/queue.v1.json` 使用 queue revision、task revision、严格字段、identity hash、record hash、共享进程锁及临时文件 `fsync + replace`。hash 用于检出损坏或非预期改写，不替代 Notification Adapter 的可信回执。
- 仓储文件缺失表示新空队列；存在但 JSON/版本/字段/hash/身份/序列损坏时失败关闭。

## 3. 排序、到期与公平性

只有 `dueAt <= trusted UTC now` 且 retry/verification backoff 已到期的记录可执行。有效优先级为：

```text
effectivePriority = priority + floor(waitingSeconds / agingIntervalSeconds)
```

排序键依次为有效优先级降序、dueAt 升序、持久 sequence 升序、taskId 升序。持续到来的新高优先任务不会永久压住较早低优先任务；39 项专项中的有界长期场景用 102 个冻结逻辑 tick 证明低优先记录在确定上界内获得机会，没有真实 sleep。

## 4. 背压、资源与静默时段

- capacity 满时返回明确 `BACKPRESSURE`，不写入被拒绝任务，也不改变既有队列。
- 静默时段与资源不足均返回明确 defer，attempt 仍为 0；不创建 WakeSession、不调用通知、不写队列、不修改资源状态。
- 资源门先调用既有 `ResourceManager.preview`。真正交付 Awakening 的 TEST 组合继续经过 `ResourceAwareWakeScheduler.request_wake`，使用同一 attempt identity 作为 WakeSession identity；没有第二资源系统。
- 静默时段只限制新机会。对已经发出的 UNKNOWN attempt 的事实核实不被静默时段或资源变化伪装成“未投递”。

## 5. 投递、UNKNOWN 与重试

一次新投递前先原子保存 `UNKNOWN + stable attemptId` checkpoint，随后才调用 Notification Adapter：

1. `DELIVERED`：保存绑定回执，进入 `COMPLETED`。
2. `FAILED` / 明确 `NOT_DELIVERED`：若未达上限，进入 `RETRY_WAIT`，按 `base × 2^(attempt-1)` 退避；到上限进入 `RETRY_EXHAUSTED`。
3. `UNKNOWN`、查询异常、回执缺失或绑定冲突：保持 `UNKNOWN`，只按原 attempt identity 查询，不创建新 attempt。
4. UNKNOWN 查询也有确定性退避，避免一个长期未知记录占住每次 tick；期间其他已到期任务仍能获得机会。

Adapter 在效果发生后进程中断时，队列 checkpoint 保持 UNKNOWN。重启后只查询原 attempt；若独立回执确认 delivered，则归账完成且不再次投递/计费/Wake。Fixture 的本地原子回执只能证明本地 TEST 语义。

## 6. 取消和终态

- `QUEUED` / `RETRY_WAIT` 可原子进入 `CANCELLED`；重复取消返回 `ALREADY_CANCELLED`。
- `COMPLETED` 不倒退；取消返回 `ALREADY_COMPLETED`。
- `RETRY_EXHAUSTED` 是终态。
- UNKNOWN 取消只记录 `cancelRequestedAt` 并触发原事实核实。可信 NOT_DELIVERED/FAILED 后才进入 CANCELLED；可信 DELIVERED 仍归账 COMPLETED。
- 重复 tick、重复 receipt 或重复 submit 均不产生第二次投递。

## 7. 可审计 Trace 与数据隔离

队列只保留 reason code、时间、稳定 ID、状态和回执 hash，不保存通知正文、凭据、Provider 响应或隐藏思维链。P11 Fixture 在任何写入前复用受保护路径检查，并继续使用 P01 `SandboxFrozenClock`。所有测试根位于独立 Temp；正式 `.continuity-data` 没有被用作 Fixture、初始化目标或迁移目标。
