### 探针与正式回归的差异

R01 原探针把 barrier 放在写入点。事务锁生效后，这个 barrier 会等待被锁挡住的第二线程；原探针还可能因没有成功返回而得到空集合的虚假 PASS。正式回归改为首写入暂停、第二线程写入信号与有界等待，要求有真实成功调用，成功 ID 必须全部可追溯，并验证跨仓储实例、重复身份、旧 revision。没有只给最后 replace 加锁。

R05 原探针要求第二次调用不抛异常，属于用户允许的两种方案之一。本次采用另一种明确允许的方案：精确重复和同身份内容冲突均明确 ResourceValidationError、第二次零写入，然后原分配仍可结算到 8。保留原探针及失败原件，正式回归使用明确异常类型，不吞异常、不弱化扣费或结算断言。

本轮新增 revision 对照最初把 `continuity.current_focus` 的 SET 值写成字符串，而该字段是列表。它在抵达写入 barrier 前被合法输入校验拒绝，表现为等待断言 FAIL；修正为单元素列表后正常覆盖 revision。该辅助构造错误不计为第九个引擎缺陷。独立审查更早的空 impact_scope 辅助错误、早期 Memory ERROR、P09 segment 10 UNKNOWN 另有各自原始记录，均不倒写。

三项补充红灯中，未持久化 update ID 与旧置信度属于 R01/R06 的直接闭合要求；R08 原有拒绝已做到零副作用，补充断言要求对外给出 `DISPATCH_BINDING_CONFLICT`，不把该诊断文字变化夸大为再次发生跨主体副作用。

### 首次全量揭示的兼容处理

首次全量 877 项中三项 ERROR 全部保留：一项 P04 来源别名的负向用例本应由仓储拒绝伪造根，R07 新合并路径却先制造了自引用，抛出了不同的领域错误。修复仅在合并结果排除指向自身的 source_memory_id；候选的原始来源链仍完整保存在 operation 中，并由原仓储在追加结果之前核实。新增对照证明“引用旧结果 + 合法新 Event”可合并，而没有声明来源的伪造根仍被原 MemoryPersistenceError 拒绝，仓储校验未变。

另外两项来自旧 `test_permissions.py`：先授予精确 scope `memory_manager`，再把它 restrict 成另一个精确名称 `memory_manager:project-only`。现有 `PermissionState.allows` 从未把冒号解释成层级；这种旧 Fixture 实际执行了本轮 R02 要求禁止的范围置换。为保留正确的权限语义，未引入前缀放行或扩大任何生产授权。仅这两项对照先显式授予 `memory_manager` 与 `memory_manager:project-only`，随后缩成后一项。其余默认 Fixture 不变；全部原断言的 AST 精确一致，新增负向明确证明仅授予前者时不得 restrict 到后者。
