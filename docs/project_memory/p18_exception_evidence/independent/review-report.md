## 唯一确认的问题：P2，连续异常时丢失原生原因

源码位置：

- `src/continuity_engine/storage/json_repository.py:444–446`
- `src/continuity_engine/storage/json_runtime_repository.py:210–212`

当前实现只把 `primary.__cause__` 接到清理异常，再清空清理异常的 `__context__`，最后执行 `raise primary from cleanup`。

在原生 `PermissionError / WinError 5` 的处理过程中，重试守卫或当前文件/版本条件可能抛出新的异常。原生错误在这种情况下位于新异常的 **隐式 `__context__`**，不一定在显式 `__cause__`。后续清理失败再次抛出主异常，会改变上下文；仅搬运显式原因不能保住最初错误。

独立探针：[test_independent_storage_final.py](test_independent_storage_final.py)。这些组合是对隔离 TEST 文件进行故障注入，不是宣称真实 Windows 同时自然发生了三重故障。

| 最小对照 | 原生错误保留 | 结果 |
|---|---|---|
| SubjectState：原生替换拒绝 → 当前授权拒绝；清理成功 | 是 | PASS |
| 同一流程，但清理另抛异常 | 否，仅剩授权拒绝与清理失败 | FAIL |
| checkpoint：原生替换拒绝 → 原准备文档被改变、版本校验拒绝；清理成功 | 是 | PASS |
| 同一流程，但清理另抛异常 | 否，仅剩版本冲突与清理失败 | FAIL |

两项失败都先验证了：替换调用仅 1 次、旧目标字节不变、顶层仍是应有的授权/版本拒绝。SubjectState 还验证了没有产生更新历史。失败断言是“异常图必须仍可找到初次原生拒绝”。测试补丁退出后按临时根所有权回收文件，不需要修改 ACL、只读属性或全局配置。

其余两项新探针通过：同一路径不同仓库实例不能借用另一实例事务资格；不同根嵌套事务复制 Context 后，退出内层会使内层资格失效，仍活动的外层可以按既有规则有限重试，外层退出后两者均不能重新获得资格。

### 为什么值得修，而不是宣布原有功能全坏

当前失败没有证明 Engine 主循环会退出，也没有证明人格、记忆、权限或实际动作被改坏。它影响的是故障证据完整性：今后再出现复合失败，可能又只留下后续错误而找不到最早的系统拒绝。这与本轮明确承诺保留原异常原因的交付要求有关，因此建议在收尾前补齐。

最小修复目标是保留主拒绝语义，并可追溯原生失败、后续校验失败及清理失败；显式和隐式原因链都需覆盖，避免循环或覆盖已有原因。无需改变重试次数/期限、拒绝政策、权限、调度、主体状态字段或运行寿命。不得为让测试通过吞掉清理错误或把失败记作成功。

## 持续运行与公共模块边界

本次既有运行源码修改限于两个存储文件。没有新增“运行多久、多少轮或多久不聊天便停止”的产品条件。原专项和独立检查覆盖了单次写入耗尽后宿主保活、释放后恢复、暂停/恢复/停止、已完成事实不再次派发，以及旧公共拒绝边界。

需要保留一个真实限制：若 PAUSE/STOP 命令本身的 checkpoint 无法保存，调用不能谎报该命令已成功提交；测试验证释放限制后重放原命令会按既有规则生效。这不等于所有磁盘故障下任意控制都能立即持久化。关键状态不可信或真实权限拒绝也没有被改成无条件继续。

因此，本次复核支持“没有发现这一存储补修改变引擎原始目标”，不支持“绝不影响任何模块”的无限保证。公共存储改动需要相关兼容验证，不能只凭修改文件少就保证零风险。
