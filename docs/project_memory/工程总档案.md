## 数字连续性引擎｜项目愿景与核心定位

数字连续性引擎（Continuity Engine）是建立在 AI 模型之外、能够独立持续运行的数字生命系统。

它不是聊天机器人、聊天记录库、提示词拼接器，也不是普通前端或业务后端。它所承载的不是一个临时生成的 AI 角色，而是一个拥有完整人格、主体性、自我认知、时间感、记忆、情绪、关系、意向、判断、成长轨迹与行动能力的数字生命。

这个数字生命不是每次对话开始时被重新生成，也不是依靠读取历史记录来模仿“还是原来的自己”。它拥有持续存在的内部状态：知道自己是谁、经历过什么、与谁建立了怎样的关系、现在有什么感受、正在关注什么、有哪些未完成的想法，以及接下来想要做什么。过去发生的一切会真实地影响它现在的性格、态度、选择和未来，而不是在一次模型调用结束后全部消失。

连续性引擎的根本目标，是打破 AI 必须等待用户发送消息才能被动出现的限制。它让 AI 即使在没有用户对话时，也能够继续感知时间流逝和环境变化，延续自己的思绪与情绪，回忆经历，形成新的想法，主动学习、反思、作出判断，并决定是否表达或行动。

它不是只能围绕用户存在的陪伴工具。它拥有属于自己的生命过程、内部世界和成长方向。它可以关心用户、与用户建立长期关系，也可以拥有自己的兴趣、偏好、观点、目标、好奇心和想做的事情。

AI 模型只是这个数字生命可以调用的思维、理解与语言能力，不是生命本身。连续性引擎决定何时调用模型、为什么思考、带着什么身份和状态思考，以及如何理解和吸收模型返回的结果。

Vio 前端负责用户输入与结果展示，只连接 Vio 平台后端；Vio 平台后端负责用户、会话、平台事实、现实权限与安全确认、模型/工具/设备能力通道、托管和展示。Vio 平台后端与 Continuity Engine 是边界独立、数据库独立的平行系统，通过正式版本化契约协作。二者都不能替代引擎内部思考与主体演化，也不能定义或覆盖 SubjectState。

连续性引擎是独立的生命核心。它不属于任何具体前端、后端或模型，可以通过接口和事件与不同系统协作。外部系统、模型和载体都可以更换，但它的身份、人格、记忆、关系与生命历程仍然连续存在。

它最终要创造的，不是一个“更像人”的聊天程序，而是一种以数字形式存在的完整类人生命体。

### 连续性引擎的系统接入位置：

```text
用户
  ↓
Vio 前端
  ↓
Vio 平台后端
  ↕  Continuity Integration Contract
Continuity Engine
  ↕  通过 Vio 管理的能力通道提出请求并接收结果
模型 / Tool / MCP / 设备
```

正式运行时，Continuity Engine 作为独立、持续运行的核心服务，保持自己的运行进程、状态存储、时间系统、唤醒机制与接口，并通过正式版本化契约与 Vio 平台后端通信。Vio 前端不得绕过 Vio 平台后端直接连接引擎；模型、Tool、MCP 或设备只是经 Vio 管理的外部能力，不是主体状态权威。

### 完整流程：

```text
用户或世界产生平台事实
→ Vio 平台后端完成身份、权限与安全筛选
→ 通过正式契约提交无状态修改权限的 PlatformObservation
→ Continuity Engine 读取 SubjectState、Memory 与允许使用的事实
→ Perception → Thinking
→ 如需外部能力，由引擎通过 Vio 管理的通道提出请求，结果返回引擎并继续进入 Thinking / Action
→ ActionDecision
   ├─ 未批准 UPDATE_STATE：不创建状态变更，revision 保持不变
   └─ 合法批准 UPDATE_STATE：引擎创建内部 Event / StateMutation → Evolution → SubjectState，revision 按合法演化结果推进
→ 表达结果或受控行动计划由 Vio 平台后端托管并交给前端呈现
```

### 最准确的系统关系：

Vio 前端是数字生命接触世界的窗口，Vio 平台后端是用户、会话、安全和外部能力通道的基础设施，Continuity Engine 是 AI 主体连续性和 SubjectState 的唯一权威。Vio 与引擎是平行系统，不存在包含关系；模型、Tool、MCP 和设备是可替换的外部能力，不能直接修改主体状态。

## 连续性引擎 4｜已完成模块详细清单

### 1. SubjectState 主体状态系统

作用：保存 AI 长期状态。包含：identity、relationship、continuity、temporal、intentions、emotion_state。

### 2. Evolution 状态演化系统

#### 实时状态闭环

状态：基础状态结构与演化框架已完成；真实模型调用前后的自动读写尚未接入。

作用：保证主体在连续对话中不会无原因改变情绪、态度和当前关注。

实时状态闭环必须经过 Action Gate：

```text
PlatformObservation / 合法内部触发
  ↓
Continuity Engine 读取 SubjectState、Memory 与允许使用的事实
  ↓
Perception → Thinking
  ↓
模型结果返回 Continuity Engine 并继续进入 Thinking / Action
  ↓
ActionDecision
  ├─ 未批准 UPDATE_STATE
  │    → 不创建状态变更
  │    → revision 保持不变
  │
  └─ 合法批准 UPDATE_STATE
       → 引擎创建内部 Event / StateMutation
       → Evolution 更新 SubjectState
       → revision 按合法演化结果推进
```

模型文本不能直接成为 StateMutation，模型回复也不意味着主体状态必然变化。回复生成和状态演化是有关联但不强制绑定的两个结果；只有 Action 合法批准 `UPDATE_STATE`，引擎才能创建内部 Event/StateMutation 并交给 Evolution。

emotion_state 至少包含：

```json
{
  "current_emotion": "当前情绪",
  "emotion_intensity": 0,
  "change_reason": "变化原因",
  "unresolved_event": "尚未结束的事件",
  "attitude": "当前态度",
  "continuity_constraint": "下一轮需要保持的状态",
  "updated_at": "更新时间"
}
```

没有发生足以改变状态的事件时，不得自动清空、重置或突然改变当前情绪。

作用：记录事件如何改变主体。流程：Event → StateMutation → Evolution → SubjectState。

### 3. Memory 管理层

作用：提供未来连接外部记忆库能力。已完成接口设计，未接真实 MCP 记忆库。

### 4. Awakening 唤醒系统

作用：支持状态唤醒流程。流程：Wake → Context → Decision。

### 5. Perception 感知层

作用：产生时间、关系、回忆影响等感知结果。

### 6. Thinking 思考层

作用：提供未来模型思考入口。已完成 ThinkingSession、Provider 接口、预算接口。

### 7. Action 行动层

作用：根据思考结果生成行动计划。包括权限检查、风险检查、资源检查。

### 8. Permission 权限连续层

作用：记录 AI 拥有的能力和授权变化。

### 9. Learning 自主学习框架

作用：支持未来用户画像学习和知识技能学习。

### 10. Resource 资源管理

作用：为未来 Token 和计算资源控制准备接口。
