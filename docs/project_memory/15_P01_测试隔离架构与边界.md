# P01 测试隔离架构与边界

> 阶段：P01——测试隔离、时间冻结、快照/分支与一键回滚
>
> 当前状态：P01 与 Engine side 均为 `ACCEPTED`；Vio dependency `NONE`；Vio/PWA production integration `DEFERRED_TO_P22`。用户于 2026-08-27 正式验收 P01。
>
> 本文件只描述 test-only 基础设施，不授予正式 Subject 回滚、生产恢复、Scheduler 或后续阶段能力。

## 1. 定位

P01 在 `continuity_engine.testing` 独立命名空间中建立一次性 Research/Test Sandbox。它不是 SubjectState、Memory、Evolution、Thinking 或任何正式运行模块的权威，也不会被正式入口自动导入。测试设施未使用或未部署时，原 Engine 闭环保持不变。

P01 固定边界：

- 每个 Sandbox 使用独立 subject、Binding、cycle、namespace、branch 和数据根。
- `environment=TEST`、`synthetic=true`、`promotionAllowed=false` 是持久化不变量。
- Fixture、Memory、Trace 与所有暂态状态只能写入 Sandbox branch。
- 人格、关系、连续性和 revision 的测试变化必须经过真实 `Event / StateMutation → Evolution → SubjectState`。
- Snapshot/Rollback 只服务测试、实验和 Research Sandbox；不得导入正式主体或改写正式 Event history。
- P20/P21 才负责正式 Subject、Owner Domain 与生产恢复。

## 2. 组件关系

```text
P01SandboxManager
  ├─ SandboxDescriptor / registry / TEST markers
  ├─ SandboxFrozenClock（主体时间）
  ├─ SandboxRuntime
  │    ├─ SubjectStateService + JsonSubjectStateRepository
  │    ├─ Event / StateMutation / Evolution
  │    ├─ SandboxMemoryRepository + MemoryService ports
  │    ├─ JsonLearningRepository / JsonResourceRepository
  │    ├─ Binding / AwakeCycle / WakeSession / ThinkSession
  │    ├─ SandboxActionRepository（test-only durable ActionSession）
  │    ├─ operation / completed-result / capability ledgers
  │    └─ synthetic test trace
  ├─ IntegrationAdapter → ContinuityInteractionService 标准交互链
  ├─ SnapshotManifest + closed-world inventory + external anchor
  ├─ Branch creation / atomic rollback
  └─ acceptance receipt / evidence export / retention / safe cleanup
```

## 3. 时间边界

每个 Sandbox branch 有持久化、timezone-aware UTC 的 `SandboxFrozenClock`。主体创建、Event、Evolution、Learning、Resource、Memory、Wake、Thinking、Action、operation/result 和 test trace 的可注入时间使用同一个 subject clock；`advance()` 只接受正时间增量并产生可预测结果。

Sandbox 创建、到期和清理由独立 maintenance clock 决定。maintenance clock 不注入 SubjectState、Event 或测试主体历史，也不改变正式运行默认时钟。

## 4. Fixture 与真实演化

`StateFixture` 必须显式声明 `synthetic=true` 和 `environment=TEST`。人格、表达偏好、关系状态、重要时刻和连续性关注通过一条 synthetic Event 及合法 StateMutation 装载；测试 Memory 使用 Sandbox 专用持久化 repository，并通过现有 `MemoryRetriever` / `MemoryInfluenceRecorder` 边界参与影响记录。Fixture 不得伪造成真实历史，也不存在导入正式主体的成功路径。

Fixture 只负责 synthetic 初始状态。P01 的正式 `changed=true` 验收不再由测试 helper 手工写 Event、Memory、Learning 或 Resource 充当，而是通过 `IntegrationAdapter → ContinuityInteractionService → Awakening → Perception → Thinking → Action → Evolution → completed result` 的现有标准 Engine 链完成。test-only validator/result factory 只解除固定生产 Binding 对 disposable TEST 身份的限制，不改变正式阶段、顺序、生命周期、Action Gate、`changed` 计算或 SubjectState 权威。

## 5. Snapshot、Branch 与回滚

Snapshot 只允许从 Sandbox 自身已知 revision 创建。创建过程先读取 19 个必需逻辑组件，再复制同一 branch 的物理 payload，并为每个组件记录：名称、唯一相对物理位置、规范化内容 hash、聚合文件 hash、revision/count、snapshot ID、source branch、subject time 和 completeness。

Snapshot 使用 closed-world inventory：branch 数据根中的每个文件必须恰好映射到一个组件；未知、遗漏、重复映射或额外文件均令创建失败并返回 `SNAPSHOT_INCOMPLETE`，且不登记部分 Snapshot。创建成功后，`snapshotId → manifestHash` 同时锚定在 Sandbox descriptor/registry；即使攻击者修改 payload、逻辑证据和 Manifest 后重算全部内部 hash，外部锚点仍会令校验返回 `SNAPSHOT_TAMPERED`。校验还绑定 sandbox/subject/namespace/branch、snapshot/component ID、创建时间、来源 revision 和安全相对路径。

Branch 从已验证 Snapshot 创建独立数据副本。回滚在同一文件系统内先构造并验证 staging，再以目录原子替换恢复 source branch；若替换中断，原 branch 从 backup 恢复并返回 `ROLLBACK_FAILED`，不得留下前后混合状态。

## 6. Promotion 与正式路径隔离

Manager 和 Runtime 的 promotion 入口均只会返回 `PROMOTION_FORBIDDEN`。测试 subject ID、Binding、cycle、namespace 和数据根不能被转为正式主体。

Sandbox 根拒绝以下配置或清理目标：

- 仓库根、正式数据根、受保护目录及相互父子重叠路径；
- 用户主目录或其父目录；
- 文件系统根、路径穿越、未登记目录或缺失/冲突 marker；
- symbolic link、Windows junction/reparse point 及其目标。

所有 P01 repository root 在 I/O 前都必须证明位于目标 Sandbox data root 内。Runtime 自报 `formalAccessCount` 仅是辅助诊断，不是充分证据；外部验收器还要在标准交互、Snapshot、Rollback、验收和清理前后比较完整正式测试根的物理 inventory/tree hash。清理前必须同时验证 registry、绝对目标、direct-child 关系、TEST/synthetic/non-promotable marker 和链接边界。

## 7. 保留与清理策略

- 成功：只有标准交互 `changed=true`、指定 Snapshot、精确 rollback、外部锚点与正式路径隔离证明共同形成有效 acceptance receipt 后，才向 Sandbox 根外的 P01 evidence 目录导出不含秘密/正文的验收证据并自动清理目标 Sandbox。
- 失败：默认保留 24 小时。
- 显式调试：正时长，最长 7 天。
- 手动清理：仅接受已登记 Sandbox ID，重复清理幂等。
- ACTIVE Sandbox 创建时即获得 24 小时 lease；进程中断或遗弃后，下一次 P01 manager 启动、Sandbox 创建/结束或显式维护入口会扫描到期的 ACTIVE/RETAINED Sandbox。没有后台线程或 Scheduler。
