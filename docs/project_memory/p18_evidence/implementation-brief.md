### 用户明确要求：默认持续运行，不是概率性启动

- 启动成功后，运行时默认持续存活、自行调度，正常入口不设置运行若干轮/若干分钟就自行退出的产品限制。不能等待下一条用户消息、网页访问或随机抽中才重新启动。
- 没有用户消息、暂无队列任务、一个 Wake/ThinkSession 结束、主体选择沉默、网页/聊天窗口/Vio/某个 Adapter 断开，均不是停止整个运行时的理由。无用户输入时仍须能依据时间和主体内部状态继续原认知链，不仅保留一个空转进程或心跳标签。
- 安静等待、让出 CPU、背压和局部退避属于仍在运行。等待应可响应控制和新的内部工作，不得忙转；不要求每秒调用模型、伪造持续思考或凭空消耗 Token。
- **整体运行控制、单项任务状态和资源可用性必须分开。** 某个模型/工具额度耗尽、能力不可用或投递暂不许可，只等待/限制受影响工作，不顺便 STOP 整个运行时；仍在现有权限和可用资源范围内处理控制、状态维护、恢复检查及其他合法工作。若所有认知工作都暂受限，如实表示等待资源，不能冒称仍在进行模型思考。
- 主体的暂停/停止意愿经已有 P15 等合法流程落地；Owner 明确暂停/关闭必须有效。停止意图应持久保留，自动恢复不能把已明确停止或归档的主体偷偷重新启动。
- 断电、操作系统休眠/终止、进程崩溃或无法继续的运行条件是实际中断，须明确报告和设计恢复，不能承诺软件永不中断。条件恢复后按已授权的恢复方式和保留状态续接，避免无界重启风暴；本轮不擅自安装开机自启或系统服务。

原规划中的“计算机会”仅是 Scheduler 分配计算时间的术语，不得解释成主体/运行时按概率存在、偶尔运行或每轮重新启动。以下涉及暂停、预算和限时测试的条款均按这一区分实现。

## 4. 实际交付目标与 DEPENDENCIES

在现有架构上补运行宿主，不平行重建 Scheduler、Wake、资源、主体状态或请求账本。优先复用实际 `SchedulerService`、`ResourceAwareWakeScheduler`、Awakening/WakeSession、ResourceManager、`build_continuity_core`/C1、P12 Memory、P14 Dynamic Mind、P15 生命周期、P16 能力与 P17 执行/回执恢复。

需要形成以下可实跑能力及对应矩阵：

1. **Engine 自有运行宿主。** 提供默认持续存活的独立进程启动、状态查询、暂停、恢复、停止入口及清晰退出原因；不依赖 Vio、Assistant、网页或用户聊天窗口。任务暂时为空不能自然退出或要求用户重新唤起。正常持续运行入口与有限步数/限时测试工具明确区分。
2. **运行生命周期。** 明确状态/操作、合法转换、调用者权限、幂等性和持久化恢复点。区分用户/主体明确暂停、计算会话结束、任务资源等待与 P15 Subject 生命周期，不能用一个 PAUSED 标签掩盖整个进程已退出。STOP 或 Adapter 断开不等于主体死亡、删除或归档。Subject SUSPEND/ARCHIVE 意图仍经原 P15 确认/Evolution 路径，Runtime 不能重启就绕过明确停止或主体已归档/删除状态。
3. **无用户输入的真实 C1 接线。** 持续运行的 Runtime 自行依据时间、内部状态与工作需要，经既有 Scheduler/Wake 调度原 C1/P14/P15，由主体链形成内容与行动。演示在没有新用户消息、没有外部任务输入时，已有内部状态仍可推动认知、反思、记忆整理和后续结果吸收，而非每次伪造一条用户消息或让 tick 直接写心理内容。可以安静等待，不强制每个 tick 调模型；但不能退化成仅等外部消息的服务。
4. **跨会话连续心智。** 多轮及重启保持同一主体身份、已有心理状态和原账本；内部内容真实影响原注意/召回/Thinking/Decision/Expression，而非仅供显示。遵循原更新职责与 Evolution/revision，不借运行时直接篡改 SubjectState、历史 Event 或客观时间。
5. **可信时间与等待。** 区分客观时间、进程内经过时间和 P14 主观时间；处理时钟回拨、跃进、重启/休眠后长时间空档。不得倒改历史时间戳、用负 elapsed 增加预算或在恢复时无界补跑所有错过 tick。空闲等待可被 STOP/PAUSE 唤醒，不忙等；采用可注入时钟进行确定性测试，不要求配置生产时间服务。
6. **统一资源与局部等待。** 自动 Wake、内部任务、模型/工具尝试都经过既有资源和权限入口；区分预计/实际消耗，后台消耗可追溯。预算耗尽只停止新增依赖该预算的调用并保留恢复点，运行宿主继续存活，能响应控制并处理其他有权限、有资源的工作，不通过退出进程实现“省额度”。合法资源恢复后自行重新评估仍有效的待处理工作，不需要额外用户聊天来激活；Owner/Subject 明确暂停、取消或失效请求仍不得自动复活。重启不能重置配额、重复分配 session 或扣费；已发生事实核实结算与新执行区分。
7. **防重复与有界恢复。** 同一主体/环境/运行数据根避免双进程同时成为有效运行者；锁/租约等方案由实际架构确定，防陈旧拥有者继续派发。复用原 P11/P17 的任务、请求、幂等和 UNKNOWN 查询语义；恢复不盲重试，不重复效果、消息、事件或 revision。Outbox 和 Runtime checkpoint 都不能成为第二套权威结果账本。
8. **可控的异常与循环。** 有界重试、退避、任务背压及重复唤醒/自激循环限制，明确受影响任务、可恢复等待和故障原因，防 CPU 忙转或无限调用。限制问题任务和相关调用，不以正常空闲、单项额度用完或单个可恢复异常为理由停止整个运行时；无法继续的进程级故障如实报告。限制基础设施调度和真实效果，不删除心理冲突、欲望或意志来“修复循环”。模型/Adapter 暂不可用应记录、等待或走合法替代路径，不让主体身份/状态消失。
9. **主动联系的完整 TEST 链。** 主体先形成联系或保持沉默的决定，经原 Expression/Action/P17 权限、资源和现实边界到 Fake 通知，再回原结果链。Scheduler 不替主体生成联系意图；时段/频率/费用检查只约束投递。暂停、撤权或到达上限时不能继续产生新通知；未知投递先查回执，不盲目重发。
10. **可观察但非第二权威。** 提供最小状态/诊断入口，分别说明进程是否存活、主体/Runtime 是否被明确暂停、认知或行动任务是否等待资源、最近活动及下一次计划检查、待恢复工作和后台资源消耗。不能只显示 RUNNING 心跳却无实际认知接线。复用原记录与结构状态，不实现 P19 完整 Inspector，不抓取 Provider 原始隐藏思维链。可持久化主体自身明确内容及既有理由摘要，不新造人格纠正规则。
