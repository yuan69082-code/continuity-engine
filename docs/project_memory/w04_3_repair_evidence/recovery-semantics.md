# 返修后的等待与恢复语义

## R1：谁入队与谁执行

`TemporaryToolRuntimeWork.needs`仍调用原native.needs，因此认知和记忆维护需求没有被关闭。读取原Scheduler当前主体/环境的全部任务身份，把已经拥有的身份留给Scheduler继续等待、查询、派发；只向本轮两个入队名额提供尚未拥有的需求。排序为到期时间、原优先级、稳定身份，没有第二队列或游标。

这修复的是入队机会被固定首项占用。原Scheduler的资源、排队、公平调度、重查时间、UNKNOWN和取消终态均不改。已拥有的UNKNOWN任务不能通过另造身份逃过查询；已完成/取消任务不重新入队。多工具真实宿主用例同时保留原native认知和维护，验证实际回执、一次效果和一次扣费。有限测试不保证任意无界输入下的公平性或时延。

## R2：一次尝试有界，连接生命周期没有固定三次封顶

一次advance最多产生一份新的清理请求。上一份自动清理如果有可信失败或部分完成回执，下一次最早时间由该回执completed_at加配置间隔得出。默认间隔直接复用P18 RuntimePolicy.retry_seconds的5秒；不是现实费用政策。参数必须是正有限数；零、负数、布尔、NaN/Infinity或文本会被拒绝。

首次明确清理失败之后保留原有立即续做资格；后续自动清理用`RETRY_CLEANUP`原请求/回执绑定退避。重开读取原记录，不重置计数、预算或等待起点。条件仍不具备返回CURRENT_CONDITIONS及静态缺项；退避内返回BACKOFF和下一次时间。不会为等待创建一批新清理请求。

已有请求明确NOT_EXECUTED时沿原身份恢复；UNKNOWN先查原事实，不新增有副作用清理；CLOSED不重复清理。每次新尝试仍通过当前主体、host/generation、控制、权限、原Action当前Context、资源与E5-A约束。撤销了使用资格不等于自动获得清理权限；清理权限失效如实等待。没有恢复旧连接使用资格或删去失败事实。

## 当前认知版本与工具步骤

真实native认知可先合法推进主体revision。此前准备的工具Context不会因此自动变成当前版本。旧版本反例仍拒绝，没有业务效果或偷偷重绑；正常对照为后续新的use/close步骤经原Wake→Perception→C1取得当前Context，再由原Action逐步核验。历史connect与原回执不改、不再发现。

测试曾尝试为close重取包含本轮临时结果的宽泛Context，close准备后该来源失效，原检查正确阻断。这个新测试生产器的问题与证据保留在[investigations.md](investigations.md)。当前修补没有授权复活失效来源，也没有改公共Context语义。

## 运行寿命与只读

工具等待只影响相应任务；真实P18宿主、认知、维护及其他合法工具保持原控制语义。PAUSE不派发，恢复重新查条件，STOP不自动复活。没有新增运行时长、tick次数或概率停机条件。

只读inspect/原查询不调用模型、执行业务、扣费或推进revision；Scheduler.query是被授权的恢复入口，与用户只读查看不同。后者不会被用作推进工作的方法。旧状态记录、原事实与历史F1/H1/F2 UNKNOWN均保留。
