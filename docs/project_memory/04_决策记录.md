# 架构决策记录

> 本文件记录由当前实现可确认的重要决定。未来修改决定时，应追加新记录并注明替代关系，不应静默覆盖历史。

## D-001：采用 domain / services / storage 分层

**决定：** 领域模型和规则放在 `domain`，业务编排放在 `services`，持久化实现放在 `storage`；外部连接另置于 `interfaces` 和 `frontend`。

**原因：** 保持核心规则不依赖具体存储、平台或 UI，便于测试和替换。

**影响：** 新功能必须先判断属于规则、用例、存储还是入口，不允许跨层偷写状态。

**未来是否可修改：** 可演进目录组织，但依赖方向和职责隔离不应在无架构评审时改变。

## D-002：SubjectState 是连续性的中心状态对象

**决定：** 主体当前状态由 SubjectState 及其 revision 表达，包含 identity、relationship、continuity、temporal、intentions 和 emotion_state 六部分。

**原因：** 需要稳定、可序列化、可比较的当前状态快照。

**影响：** 其他模块观察或提出变更，但不各自维护一份竞争性的主体状态。

**未来是否可修改：** 字段可通过兼容迁移扩展；不能无迁移地改变已有序列化语义。

## D-003：正式状态变化只能经过 Event → Evolution

**决定：** Permission、Learning、Thinking 或 Action 均不能直接修改 SubjectState；批准的变化先生成 Event/StateMutation，再由 Evolution 应用。

**原因：** 保留原因、来源、前后差异和可审计历史。

**影响：** 看似简单的字段更新也必须遵守演化入口。

**未来是否可修改：** 不建议修改；这是核心不变量。

## D-004：使用 revision 和 expected_revision 防止覆盖

**决定：** 状态更新和行动评估校验输入 revision。

**原因：** 防止基于旧状态生成的变化覆盖新状态。

**影响：** 调用方必须携带自己看到的 revision，并处理冲突。

**未来是否可修改：** 可替换为更强的并发机制，但不能取消并发保护。

## D-005：Memory 管理层不拥有长期记忆存储

**决定：** Memory 负责检索请求、相关性判断和影响记录，长期保存通过可插拔 Retriever/Recorder 或未来 MCP 完成。

**原因：** 避免核心绑定某个向量库、平台或记忆产品。

**影响：** 当前不能把 MemoryRetrievalResult 等同于已存在的长期记忆数据库。

**未来是否可修改：** 可增加适配器，不建议把具体外部存储实现放入领域核心。

## D-006：每次唤醒都形成 WakeSession

**决定：** 手动、定时或事件唤醒均记录原因、时间、输入 revision、所见上下文、最终决策和成功状态。

**原因：** 自主运行必须可追溯，而不是无记录的后台行为。

**影响：** Wake 是后续 Perception/Thinking/Action 会话的追踪起点。

**未来是否可修改：** 可增加原因类型和指标；不可取消基础审计。

## D-007：Perception 是 Thinking 唯一直接输入层

**决定：** 主流程固定为 Wake → Perception → Thinking，Thinking 不再直接读取 WakeContext 或数据库。

**原因：** 分离“观察到什么”和“如何判断”，减少耦合。

**影响：** 新的感知信息应先进入 PerceptionResult，再供 Thinking 使用。

**未来是否可修改：** 若需旁路输入必须架构评审；默认保持。

## D-008：Perception 只读

**决定：** Perception 只能观察、理解和生成感知，不能修改 SubjectState。

**原因：** 感知不是行动，也不应暗中产生状态副作用。

**影响：** 感知结果导致的变化仍需 Thinking → Action → Evolution。

**未来是否可修改：** 不建议修改；这是核心边界。

## D-009：ThinkingProvider 可插拔且不保存完整思维链

**决定：** Thinking Engine 通过 Provider 协议调用未来模型，只保存思考过程摘要、输入概况和结果。

**原因：** 避免绑定 GPT、Claude 或本地模型，并控制隐私与日志风险。

**影响：** 模型接入必须实现标准 Provider；日志不得写入模型完整内部推理。

**未来是否可修改：** Provider 可扩展；摘要审计原则应保持。

## D-010：Action 只决定和规划，不执行

**决定：** ActionIntent 不是最终批准，ActionDecision 和 ActionPlan 也不是执行结果；计划状态不包含 EXECUTED。

**原因：** 决策与真实外部副作用必须分离。

**影响：** CONTACT_USER、USE_TOOL、REQUEST_MEMORY 当前只生成计划，不得伪造成功。

**未来是否可修改：** Execution Engine 可作为独立阶段新增，但不得混入 ActionService。

## D-011：Action 必须经过权限、风险和资源评估

**决定：** 缺少/撤销/过期/越界权限会阻止或拒绝；HIGH/CRITICAL 风险不能自动批准；资源使用确定性估算。

**原因：** 让行动决定受约束、可复现、可测试。

**影响：** 同一输入应产生确定性结果，所有拒绝、阻止和延后必须有原因。

**未来是否可修改：** 规则可版本化增强，最低安全规则不能静默弱化。

## D-012：权限连续层与行动时 PermissionCheck 分离

**决定：** PermissionState/History 表达“长期拥有什么权限以及如何变化”；Action PermissionProvider 表达“本次行动是否可获准”。

**原因：** 一次判断不能替代权限生命周期和来源审计。

**影响：** Action 通过 PermissionContext 获取当前权限视图，PermissionService 不执行行动或修改 SubjectState。

**未来是否可修改：** 可统一适配接口，但不能丢失历史层与评估层的语义区别。

## D-013：学习必须经证据、验证、确认和 Evolution

**决定：** 单次事件不能改变长期特征；候选需多次独立一致证据、置信度阈值和验证，固化/回滚通过 Event → Evolution。

**原因：** 防止偶然事件或错误判断永久改变人格。

**影响：** LearningService 只管理候选、证据和建议，不训练模型，也不直接写状态。

**未来是否可修改：** 阈值和验证策略可版本化；禁止单次自动永久固化的原则应保持。

## D-014：主动运行最终必须收口到资源检查

**决定：** Wake、Thinking 和 Learning 在启动高成本工作前应向 ResourceManager 申请预算；新增主动运行入口不得继续绕过资源检查。

**原因：** 防止无限自主运行，并为未来模型调用提供统一约束。

**影响：** 当前已经存在 ResourceManager、Thinking 预算连接、Learning 可选连接和 ResourceAwareWakeScheduler，但 AwakeningService 仍可被直接调用，Learning 的资源管理器也可不配置。因此统一强制入口属于尚未完成的工程约束。资源不足时采用降低深度、延迟或等待，而不是无限透支。

**未来是否可修改：** 可接真实计量，但保留预算与追踪机制。

## D-015：外部入口不得绕过 PermissionContext 和 ResourceManager

**决定：** API、MCP、Skill 和前端调用通过接口安全门进入核心。

**原因：** 适配器不应成为绕过权限或资源规则的后门。

**影响：** 新入口必须复用统一访问检查，不得直接访问仓储修改状态。

**未来是否可修改：** 安全实现可增强；检查原则不可取消。

## D-016：前端只负责输入、展示和通信

**决定：** 浏览器端不保存 SubjectState、记忆、人格，不执行权限判断或自主逻辑。

**原因：** 保持核心唯一事实源，并允许前端替换。

**影响：** 前端调试视图是服务端状态投影，不是本地状态副本。

**未来是否可修改：** 可增加 UI 与缓存，但核心状态和授权决定不能下放到不可信前端。

## D-017：本地演示首次初始化必须显式进行

**决定：** 本地前端通过 `--initialize` 明确创建初始数据，后续正常启动不隐式重置。

**原因：** 避免演示入口在不知情时覆盖连续状态。

**影响：** 首次使用命令与日常启动命令不同。

**未来是否可修改：** 可改为引导式初始化，但不得静默重建已有状态。

## D-018：兼容旧编排入口

**决定：** 保留 `wake_perception_thinking_service.py`，同时提供完整 Action 编排入口。

**原因：** 避免无理由删除已有公共接口。

**影响：** 当前兼容服务引用内存 Action 仓储，是已知分层例外；未来需明确弃用周期后再清理。

**未来是否可修改：** 可以，在提供迁移说明、弃用版本和测试后删除。

## D-019：Continuity Engine 位于 AI 模型之外

**决定：** Continuity Engine 是独立于 GPT、Claude、本地模型等具体模型的连续性层。引擎负责身份、主体状态、记忆影响、时间、感知、权限、演化与自主行为约束；模型未来负责语言理解与生成。

**原因：** 主体连续性不能绑定某个模型、一次对话或某个平台，否则更换模型或入口会破坏长期状态。

**影响：** 模型必须通过可插拔 Provider/Adapter 接入；SubjectState、演化记录和权限资源规则仍由引擎持有。Vio 平台后端与 Continuity Engine 是边界独立、数据库独立的平行系统，通过正式版本化契约协作；Vio 前端只连接 Vio 平台后端，模型、Tool、MCP 和设备也不是主体状态权威。

**未来是否可修改：** 不建议修改；这是工程总档案 v1.0 的项目定位。

## D-020：以实时状态闭环作为模型接入目标

**决定：** 真实模型接入后的标准交流路径必须经过 Action Gate：`PlatformObservation / 合法内部触发 → 读取 SubjectState、Memory 与允许使用的事实 → Perception → Thinking → 模型结果返回引擎并继续进入 Thinking / Action → ActionDecision`。未批准 `UPDATE_STATE` 时不创建状态变更且 revision 保持不变；只有 Action 合法批准 `UPDATE_STATE`，引擎才能创建内部 Event/StateMutation，并通过 Evolution 更新 SubjectState 与推进 revision。

**历史背景：** 本决定最初以“模型生成回复 → 生成 StateMutation → Evolution”概括实时闭环。该表述在 Action Gate 尚未明确时用于说明状态需要在交互之间连续，但可能被误读为模型回复必然改变主体状态；此旧语义现已被 `Continuity Integration Contract v1.1`、D-025 和本次定点修正取代。

**原因：** 每次交互都应继承连续状态，但回复生成和状态演化是有关联而不强制绑定的两个结果。模型文本不是受信状态命令；只有经过 Thinking、Action、权限/风险/资源约束和 revision 校验的合法更新，才能进入正式演化。

**影响：** 模型文本不能直接成为 StateMutation，模型回复不意味着主体状态必然变化。当前 v0.1 已完成状态、Memory 接口、Mutation/Event、Evolution、Action Gate 和持久化框架，但真实模型与 Vio 能力通道尚未接入；无合法批准的 `UPDATE_STATE` 时 revision 必须保持不变。

**未来是否可修改：** 可扩展上下文来源和编排细节，但 Action Gate 以及 StateMutation/Evolution 的正式写入边界不可绕过。

## D-021：框架完成与真实能力接入分别记录

**决定：** 工程档案中的“框架完成”只表示模型、规则、服务、仓储或适配接口已经存在并经过当前测试；真实模型、MCP、外部记忆、外部执行、后台运行、平台权限和真实计费必须单独标记为未完成，直到实际接入并验收。

**原因：** Provider、Adapter 或接口预留容易被误读为外部能力已经可用。

**影响：** 路线图、模块清单、CHANGELOG 和交接说明必须同时写明内部完成范围与外部缺口。

**未来是否可修改：** 状态可在真实能力完成验收后更新，但不得提前声明完成。

## D-022：数字生命系统是长期愿景，不是 v0.1 能力声明

**决定：** 将 Continuity Engine 的长期方向定义为位于 AI 模型之外、能够独立持续运行的数字生命系统；该愿景用于指导身份、人格、记忆、关系、时间、意向、判断、成长和行动能力的长期架构，不作为当前 v0.1 已完成能力或发布验收结论。

**原因：** 项目的目标不是只保存聊天历史或在每次对话中重新生成角色，而是让过去经历能够持续影响当前状态和未来选择；同时必须避免把愿景误写为已经存在的自主运行能力。

**影响：** 所有工程档案必须同时标注长期愿景与当前边界。独立常驻运行、完整时间/环境感知、自主内部思考、主动表达和真实行动在完成接入与验收前均属于未来规划。

**未来是否可修改：** 愿景可由项目所有者重新确认或细化；任何改变不得静默改写当前能力事实。

## D-023：引擎、前端、业务后端与模型工具职责分离

**决定：** Vio 前端是数字生命接触外界和表达结果的窗口，只连接 Vio 平台后端；Vio 平台后端负责用户、会话、平台事实、现实权限与安全确认、模型/工具/设备能力通道、托管和展示。Vio 平台后端与 Continuity Engine 是边界独立、数据库独立的平行系统，通过正式版本化契约协作。Continuity Engine 持有 AI 主体身份、连续状态、记忆影响和主体演化，是 SubjectState 的唯一权威；AI 模型、Tool、MCP 和设备只是可调用的外部能力。

**原因：** 连续性不能由某个界面、业务平台或模型会话定义，否则替换载体或能力提供方会破坏主体连续。

**影响：** Vio 前端不得绕过 Vio 平台后端直接连接引擎，Vio 也不得把状态投影回灌为权威状态；外部能力结果不能直接定义或修改 SubjectState。当前本地 HTTP 和调试前端不等于正式产品前端，仓库也不包含 Vio 平台后端或正式连接实现。

**未来是否可修改：** 外部系统的实现与通信协议可以替换；引擎作为连续性中心的职责不应在无架构评审时改变。

## D-024：正式持续运行采用独立核心服务形态

**决定：** 未来正式运行时，Continuity Engine 应保持独立进程、状态存储、时间系统、唤醒机制和接口，并通过正式版本化契约与 Vio 平台后端通信。Vio 将通过身份、权限和安全筛选的平台事实作为无状态修改权限的 PlatformObservation 交给引擎；引擎通过 Vio 管理的通道请求模型、Tool、MCP 或设备能力，结果必须返回引擎继续进入 Thinking / Action。只有 Action 合法批准 `UPDATE_STATE` 时，引擎才创建内部 Event/StateMutation 并经 Evolution 更新 SubjectState；否则不发生状态变化且 revision 保持不变。表达结果或受控行动计划再由 Vio 托管并交给前端呈现。

**原因：** 只有让外部结果回到连续性中心并经过认知与 Action Gate，才能使模型、工具和载体变化时仍保持身份与生命历程连续，同时避免把模型文本或执行结果误当成必然状态变化。

**影响：** 当前进程内 API、本地 HTTP、适配器接口和单次编排只是未来部署的基础，不代表独立常驻服务、Vio 契约通信、真实模型/工具调用或自主运行已经完成。

**未来是否可修改：** 具体传输技术可按规模调整，但 Vio 与引擎的平行系统关系、正式版本化契约、结果回流引擎、Action Gate 和正式状态变化经 Evolution 的边界必须保持。

## D-025：正式接受 Continuity Integration Contract v1.1

**决定：** Continuity Engine 于 2026-07-30 通过《Engine Contract Final Read-Only Short Confirmation v1》正式接受 `Continuity Integration Contract v1.1`。长期架构和第一轮机器契约语义已经闭合；双方工程档案同步、引擎定点文档修正和双方最终只读复核均已完成，双方档案一致。现在允许双方共同制定第一轮最小连接施工提示词，但不授权开始代码施工或共享测试。

**审核历史：**

1. 《Engine Integration Contract Response v1》完成首次边界审核并提出修订要求。
2. 《Engine Contract Second Review Response v1》因七个第一轮契约阻塞项给出“暂不接受”的阶段结论。
3. 《Engine Contract Final Read-Only Confirmation v1》确认长期架构一致，但因四类机器契约精度问题继续给出“暂不接受”的阶段结论。
4. Vio 完成最后文档校准后，《Engine Contract Final Read-Only Short Confirmation v1》独立复核通过；此前“暂不接受”继续作为真实历史快照保留，当前唯一有效状态为正式接受 v1.1。

### 长期权威与系统边界

- Vio 与 Continuity Engine 是两个平行系统，数据库保持独立。
- Vio 前端只连接 Vio 平台后端，不得绕过平台后端直接连接 Continuity Engine。
- Continuity Engine 是连续性主体和 SubjectState 的唯一权威；Vio 只保存投影、缓存和审计材料。
- Vio 负责用户、助手、会话、平台事实、现实权限与安全确认、外部能力通道、托管和展示。
- PlatformObservation、Vio Event 和摄取回执均不是引擎内部 Event，不得携带或生成 StateMutation，也不能推进 SubjectState revision。
- 模型、Tool、MCP 或设备结果必须返回引擎继续进入 Thinking / Action；只有 Action 合法批准 `UPDATE_STATE`，正式状态变化才可经过引擎内部 `Event / StateMutation → Evolution → SubjectState`。没有获批状态更新时 revision 保持不变。
- 三层数据空间边界已确认，但 User Private Data、AI Private Space 和 Shared Space 的实际跨系统读写不参加第一轮测试。

### 第一轮 Schema registry

第一轮 registry 只注册三份 JSON Schema Draft 2020-12：

1. ContinuityInteractionRequest：`urn:vio-live:continuity-integration:schema:request:first-round-v1`
2. message_created PlatformObservation：`urn:vio-live:continuity-integration:schema:platform-observation:message-created:first-round-v1`
3. message_version fact：`urn:vio-live:continuity-integration:schema:platform-fact:message-version:first-round-v1`

顶层请求中的两个 `$ref` 必须分别精确解析到第 3 和第 2 个 URN。禁止文件相对路径、网络回退或双方自行定义别名。所有对象使用 `additionalProperties: false`；验证器必须启用 `format: date-time` 断言，第一轮时间只接受以大写 `Z` 结尾的 RFC 3339 UTC。`facts` 与 `observations` 均固定为恰好一项，消息正文只允许出现在唯一 `message_version` fact 的 `content` 中。

正式 conformance vector、三处 identity、conversation/message/version 引用、唯一 observationRef 和正文位置必须同时通过 Schema 与交叉字段校验。

三项最终一致性哈希为：

### 幂等、revision 与投影

- Schema、requestHash 和完整 SubjectBinding 验证通过后，相同 `requestId` 对应不同 `requestHash` 时，第一轮唯一错误是 `IDEMPOTENCY_KEY_REUSED / never`；`IDEMPOTENCY_CONFLICT` 不得作为别名。
- 完整 SubjectBinding 验证通过后，只要 `expectedEngineRevision != currentEngineRevision`，无论较大或较小，都返回 `REVISION_CONFLICT / reassemble`；绑定验证失败时不得泄露当前 revision。
- 投影内容唯一键为 `subjectId + currentRevision`；请求与投影关联键为 `requestId`；`engineUpdateId` 仅在非 `null` 时唯一。
- `changed=false` 时 revision 不变且 `engineUpdateId=null`；多个无变化请求可以关联同一 revision 的同一投影。
- `changed=true` 时 revision 只增加一次，`engineUpdateId=StateUpdateRecord.update_id`。
- 第一轮只使用最小 snapshot，不使用 delta；同一 `subjectId + currentRevision` 不得存在内容、`contentHash` 或 `stateHash` 不同的第二份投影。
