> P11 现行门：P00—P11 = ACCEPTED；P11 / P11 Engine side / P11-01—P11-12 = ACCEPTED；P11 Vio dependency = NONE；P12—P23 = NOT_STARTED；PLANNING_CONFLICT = NONE；EVIDENCE_CONFLICT = NONE（仅表示现行验收阻断已闭合）。D-058 已登记用户正式验收。监工独立原反例 2/2 PASS、P11 45/45 PASS（8.371 秒）；39/833 全量等修复前结果继续作为历史保留。本次仅验收归档，不运行全量。[P11 验收入口](58_P11_测试索引与验收入口.md#p11-accepted)。

## 1. 档案先行

任何新增功能开始前，必须先写清：

- **新增原因：** 解决什么连续性问题，为什么现有模块不能完成。
- **影响范围：** 涉及哪些 domain、services、storage、interfaces、frontend、数据格式和公共接口。
- **测试结果：** 计划覆盖哪些正常、边界、失败、重启和兼容场景；完成后记录实际结果。
- **是否进入核心：** 明确属于核心不变量、可插拔 Provider/Adapter、外部集成、实验功能或仅前端展示。

如果功能尚未获准，先写入 `07_待确认事项.md`，不能直接以“未来需要”为理由实现。

## 2. 分层职责

### domain

- 放置领域模型、值对象、枚举、规则和业务不变量。
- 不读取数据库、文件、网络或前端状态。
- 不依赖 services、storage、interfaces 或 frontend。

### services

- 负责用例编排、上下文组装、Provider/Repository 协调和事务边界。
- 不把外部执行结果伪造成成功。
- 不绕过 Evolution 直接改 SubjectState。

### storage

- 实现仓储协议、序列化、保存、读取、列表和历史。
- 不决定感知、思考、行动、学习或权限业务规则。
- 数据格式变化必须考虑版本、兼容读取和迁移测试。

### interfaces

- 将 API、HTTP、MCP 或 Skill 请求转换为核心服务调用。
- 所有外部调用必须经过 PermissionContext 和 ResourceManager。
- 不直接修改仓储中的核心状态。

### frontend

- 只负责输入、展示、通信和必要的 UI 临时状态。
- 不保存 SubjectState、Memory、PersonalityTrait 或权限真相。
- 不实现感知、思考、行动或学习规则。

## 3. 核心状态修改规则

所有正式 SubjectState 变化必须遵循：

```text
变更请求 / Approved UPDATE_STATE / Permission Change / Learning
                            ↓
                    Event / StateMutation
                            ↓
                         Evolution
                            ↓
                 SubjectState + UpdateRecord
```

禁止：

- ActionService 直接改 SubjectState。
- PermissionService 直接改 SubjectState。
- LearningService 直接改 SubjectState。
- Perception 或 Thinking 产生隐藏副作用。
- 外部 API、MCP、Skill 或前端直接写 JSON 状态文件。
- PlatformObservation、模型文本、Tool/MCP/设备结果直接成为 Event/StateMutation；这些输入必须先返回引擎并经过 Thinking / Action，只有合法批准的 `UPDATE_STATE` 才可进入正式状态演化。

状态更新必须校验 expected_revision，并保存来源、原因和前后差异。

## 4. 会话与审计

- Wake、Think、Action 和未来 Execution 都必须有独立 session_id 并可相互追踪。
- 拒绝、阻止、延后、降级和冲突必须保存明确原因。
- ActionPlan 不是执行结果；未实际执行不得标为成功。
- Thinking Log 只保存摘要，不保存模型完整思维链。
- 权限、学习和资源变化必须保留历史。

## 5. 可插拔接口

- 具体 AI 模型必须实现 ThinkingProvider，不得渗入领域模型。
- 外部记忆必须实现 MemoryRetriever/Recorder 端口。
- 平台权限判断通过 PermissionProvider/PermissionContext 接入。
- MCP、Skill、工具和消息渠道均属于适配或执行层，不属于核心领域。
- 确定性本地实现应保留，便于无外部依赖测试。

## 6. 权限、风险和资源

- 主动运行和外部入口必须经过资源检查。
- 行动必须经过权限、风险和资源评估。
- 缺失、撤销、过期或越界权限不得通过。
- 需要用户确认的行动不得标为可自动执行。
- HIGH 或 CRITICAL 风险不得自动批准。
- 资源不足时优先降级、延迟或等待，禁止无限透支。
- 不得自动申请、扩大、恢复或购买权限/资源。

当前实现说明：ResourceManager 和多个资源感知入口已经存在，但直接 AwakeningService 调用及未配置 ResourceManager 的 LearningService 仍可绕过统一检查。本条是后续新增入口必须遵守、并需要逐步完成收口的工程规范，不应被解释为当前所有路径均已强制执行。

## 7. 测试要求

每个功能至少根据风险覆盖：

- 领域模型与校验。
- 正常流程和失败流程。
- revision 冲突和并发覆盖防护。
- 权限缺失、撤销、过期和确认路径。
- 资源不足、降级和延迟路径。
- JSON 保存、重启恢复和历史追溯（如有持久化）。
- 无外部调用/无状态副作用边界。
- 旧公共入口和历史测试回归。

当前基线命令：

```powershell
$env:PYTHONPATH = "src"
python -m unittest discover -s tests -q
```

当前基线结果：397 项通过（P01 施工前 355 项 + P01 专项 42 项）。新增测试后必须更新本数字，不得只报告新增测试。

第一轮连接持久化还必须遵守：completed 结果不可覆盖；同 requestId/同 hash 只重放第一次完整结果；同 requestId/不同 hash 明确报告冲突；同 subjectId+currentRevision 不得出现不同投影；非空 engineUpdateId 唯一；JSON 写入采用明确格式版本、UTF-8、flush/fsync 和原子替换。账本查询不能取代 Adapter 的 Schema、Binding、幂等与 revision 验证顺序。

E3 operation journal 必须使用稳定的 operation/response/internal event 身份和单向阶段推进；恢复时应优先复用已持久化 checkpoint，并以稳定内部 eventId 检查已经提交的 Evolution，禁止生成第二次 Event 或重复推进 revision。每个 JSON 文件可以独立原子保存，但没有统一事务介质时不得宣称 result ledger、operation journal 与 SubjectState/Event 仓储跨文件原子。`ContractTestAdapter` 仅限 test-only 进程内调用，不得静默挂接到现有 API、HTTP、UserInteraction、MCP、Skill 或网络入口。

双方共享验收 Runner 必须保留在 `tests/shared/`，要求显式受控 `--data-dir`，stdin/stdout 只使用逐行 UTF-8 JSON，不得改写 Vio 的 requestHash，不得输出日志或新增第五类错误 envelope。空目录只能使用现有 bootstrap 初始化一次；非空目录只能完整验证和恢复，不能自动修复。新请求身份必须跨进程唯一，已完成请求必须重放第一次完整结果。该 Runner 不得注册正式 CLI、HTTP、Socket、生产配置或生产数据路径。

E4 正式本地入口必须与测试 Runner 隔离：`ContractTestAdapter` 和正式 `IntegrationAdapter` 只能调用同一个 `ContinuityInteractionService`，不得复制领域链或验证顺序。正式 Binding 只能通过显式 init 持久化，serve 不得隐式创建或修复状态；HTTP 固定 `127.0.0.1`、串行处理、Bearer 令牌不落盘、不启用 CORS。第一阶段所有响应必须声明并执行 `Connection: close`，每条连接必须使用正有限读取超时（默认 10 秒）；未知方法、可响应解析错误、慢请求和普通断连不得产生默认 HTML、traceback 或连接复用污染。旧调试 HTTP、APIService/UserInteractionService 和 JSONL Runner 不得接入正式装配。Vio V3 与 Engine E4 的第一阶段正式本地回环验收已经通过；该结论不得写成真实模型、公共用户链路、外网或生产部署已经实现。

E4 domain 恢复必须遵守 D-032：任何持久化副作用前先保存稳定恢复身份，完成后再保存不可逆 checkpoint；operation journal 与 Awakening/Thinking/SubjectState/update/result 仓储共同确定恢复事实。已完成 WakeSession 与 ThinkSession/ThinkingResult 必须复用，不得 completed→running、不得再次调用已完成 ThinkingProvider、不得生成第二个主体经历。恢复所需快照只能保存结构化 WakeContext、PerceptionResult、结果和摘要，不得保存完整模型思维链。旧格式部分状态只在候选唯一且所有身份/引用/revision 一致时迁移；缺失、多个候选、running/failed 或矛盾状态必须失败关闭。Evolution 与 completed result 继续保证 Event、StateUpdateRecord、revision、responseId 和 completedAt 不重复、不覆盖。

E5-A Capability 必须遵守 D-034：Engine 决定是否提出能力请求并持久化稳定 request/attempt/ThinkSession 身份，外部现实执行不属于 Engine；CapabilityResult 必须在任何结果持久化或主体副作用前通过严格 Schema、去空白后的成功输出非空校验、hash、subject/binding/request/attempt、终态和时间一致性校验，其中 started/completed 均不得早于已持久化请求 createdAt。之后才能恢复原 Thinking 并进入 Action Gate。结果不得携带 StateMutation，不得跳过 Thinking/Action，不得在恢复时重复调用已完成 Provider 或覆盖首次终态。重复 `init` 必须按持久化历史选择校验模式并保持 Binding、状态、revision、operation、request、attempt 和结果不变；`serve` 的模式保护不得因此放宽。默认 deterministic 模式必须兼容 E4；独立 capability 协议不得修改 v1.1。Vio V4、受控 S4 与首次 S4-Live 已验证这些规则；首次真实单次通过不授权重复调用、通用 Provider 或生产能力。后续真实供应商、正式身份、真实 `UPDATE_STATE`、密钥或费用扩展仍需单独授权和现场验收，密钥不得进入 Engine、SubjectState、Memory 或普通日志。

S4-Live 或后续真实外部能力验收还必须使用明确隔离、不可晋升的测试身份与仓库外沙箱；归档只能记录结构化事实、计量和状态，不得保存 API Key、Authorization 值、供应商原始完整响应或用户消息正文。供应商费用未最终报告时必须保留 `not_reported`，不能由界面暂时显示值推断最终绝对费用。可销毁沙箱清理不等于时间冻结、时间线分支、主体回滚或删除正式数据能力。

## 13. 完成定义

一个功能只有同时满足以下条件才可标记完成：

1. 需求范围明确且已获批准。
2. 领域边界和状态修改路径正确。
3. 必要接口与存储实现完成，或明确标为仅设计。
4. 正常、失败、边界和回归测试通过。
5. 不伪造外部执行、AI、MCP、Token 或权限结果。
6. 本工程档案、README 和 CHANGELOG 已同步。
7. 未实现能力明确列出。
8. “已完成、部分完成、未实现、未来规划”的状态与实际代码一致。

## 14. P00—P23 阶段门与 Planning Conflict

- 现行全周期施工必须按 P00—P23 顺序执行；不得省略、合并、弱化、替代、降级、提前施工或调整依赖。
- 阶段状态只允许 `NOT_STARTED`、`IN_PROGRESS`、`BLOCKED`、`IMPLEMENTED_NOT_ACCEPTED`、`ACCEPTED`。
- Codex 完成本地实现和核查后最多写 `IMPLEMENTED_NOT_ACCEPTED`；只有规划监工窗口核查且用户明确验收后才可写 `ACCEPTED`。
- 每阶段必须维护 Planning Item → Code Change → Test → Acceptance Result → Status → Evidence → Blocking Dependency → User Decision。
- 发现规划与代码、依赖、环境或平台冲突时，必须 `STOP CURRENT ITEM` 并返回 `PLANNING_CONFLICT`；用户决定前不得继续写入绕过。
- P01 测试/实验/Research Sandbox 恢复不得冒充 P20/P21 正式 Subject、Owner Domain 或生产恢复。正式恢复未就绪时返回 `RECOVERABILITY_NOT_READY`。
- P00 是 Engine/Vio 运行断开与独立升级起点；P10 只负责从 P09 C1 创建 Assistant 分支和独立仓库；P22 才是 Vio/PWA 第一正式 World Adapter 的生产重连。
- P01—P21 必须在 Vio process、repository、data root、network 和 credentials 均不可用时独立施工与验收；不得把 Vio cooperation、shared acceptance 或跨仓运行列为这些阶段的完成条件。
- Reality Boundary 只控制已形成行动的现实副作用，不得限制或修改 Thought、Emotion、Desire、Will、Personality、Relationship、Self-Narrative 或内部心理冲突。

## 15. P01 TEST Sandbox 规范

- P01 代码必须留在清楚标识为 test-only 的 `continuity_engine.testing` 命名空间，正式入口不得隐式导入或依赖它。
- 每个 Sandbox 必须持久化独立 identity/Binding/cycle/namespace/branch/root，以及 `environment=TEST`、`synthetic=true`、`promotionAllowed=false`。
- Fixture 和暂态人格/关系/连续性变化必须经过 Event/Evolution；禁止直接改写 SubjectState JSON。
- Snapshot 只有覆盖全部登记组件、closed-world physical inventory、唯一组件映射并通过规范化内容、物理文件、revision/count 和外部 anchor 校验后才可标记 complete；未知/遗漏/重复映射必须返回 `SNAPSHOT_INCOMPLETE`，重算内部 hash 的篡改必须返回 `SNAPSHOT_TAMPERED`。
- `changed=true` 验收必须经过唯一正式 Engine 交互链并产生真实 Wake/Think/Action/operation/result；测试 helper 手工写 Event 或 ledger 不能替代标准交互证据。
- 成功 evidence 必须由绑定交互、Snapshot、exact rollback、anchor 和正式路径隔离的 acceptance receipt 产生；未完成 round trip 必须返回 `ACCEPTANCE_NOT_READY`。
- Rollback 必须先验证、再原子替换，并能在失败时恢复原 branch；禁止删除或篡改正式 Event history。
- subject clock 与 maintenance clock 必须分离；不得以 P01 到期扫描提前实现 P11 Scheduler。
- ACTIVE 创建即有 24 小时 lease；成功 receipt/evidence export 后自动清理；失败默认 24 小时；显式调试最多 7 天；手动/到期清理只允许已登记 direct-child Sandbox。
- 仓库、正式数据、home/父目录、受保护路径、未知/缺 marker 目录和 link/junction/reparse target 一律拒绝清理。
- promotion/import-to-formal 必须不存在或稳定返回 `PROMOTION_FORBIDDEN`。
- P01 只服务测试/实验/Research Sandbox；正式 Subject/Owner Domain 恢复属于 P20/P21。

## 16. P02 宿主中立模型能力规范

- P02 只能通过 E5-A 唯一 `model.generate` durable CapabilityRequest/CapabilityResult 通道恢复原 ThinkSession；禁止建立平行 Capability、Thinking、Action、operation/result 或主体结果状态机。
- Provider Port、Profile policy、Fake Provider、execution/usage/test-credit ledger 不拥有 Subject Authority，也不得直接读取或修改 SubjectState、Event、Memory、人格、关系、情绪、Desire、Will、Decision 或 Evolution。
- Provider 候选必须先成为严格验证的 CapabilityResult，再经原 ThinkSession、Thinking、Action 与 ReplyComposer；禁止候选直出或绕过 Action Gate。
- P02 的 Provider/Model、1024 单次/10240 每日 synthetic Token、每次成功 1 test-credit 和 fallback 关闭均为可替换测试 Profile，不是永久供应商绑定或真实价格。
- `UNKNOWN`/timeout 必须查询原 execution；明确未执行或 retryable 且显式批准时才允许下一 attempt。重复 request、查询和响应丢失恢复不得重复 execution、credit、Action 或主体结果。
- UNKNOWN/TIMEOUT 的原始 Provider fact 不得覆盖；同 attempt 的后续明确终态必须以单调 query resolution 追加并参与崩溃恢复。查询仍未知时保持等待；只有明确 `NOT_EXECUTED` 才允许受控新 attempt。
- Provider 调用前必须把 `maximumTokens` 收窄为单次上限与当日剩余额度的较小值。Provider 已执行但返回越限 usage 时，执行和 synthetic credit 事实必须留账，候选必须被 `RESOURCE_EXHAUSTED` 阻断，不能进入 Thinking/Action/ReplyComposer，也不能盲目重试。
- P02 usage/test-credit 在保存和每次加载时都必须与唯一成功 Provider fact 交叉验证 execution/capabilityRequest/attempt、Provider/Model、input/output/total token、UTC usage day、recordedAt、deterministic usage identity 和 Profile credit；任一不一致必须失败关闭。
- 冻结 `vioLedgerEntryId` 只能填入 Engine 本地确定性兼容引用，不得据此访问 Vio。P02 Vio dependency 为 `NONE`。
- P02 禁止 Provider SDK、网络、API Key、真实 usage/cost 和隐藏 Chain-of-Thought 持久化；真实 Provider 与 Vio/PWA production integration 后置 P22。
- P02 完成本地实现后最多标记 `IMPLEMENTED_NOT_ACCEPTED`；未经用户验收不得进入 P03。

## 17. P03 Event 与 Timeline 规范

- Event 是客观历史事实权威；SubjectState 是当前主体状态唯一权威；Timeline 只能从 Event/StateUpdateRecord 计算，禁止另建可写 Event Store。
- 新 Event 三时间必须带时区并满足 occurredAt ≤ observedAt ≤ recordedAt；显式 Event 应用时还必须满足 recordedAt ≤ appliedAt，且 `apply_event` 只读取一次时钟并把同一 appliedAt 传给 Evolution。缺失时间必须以 `PARTIALLY_COALESCED` 或 `LEGACY_COALESCED` 如实标记，不得伪称独立测量。
- eventId 是内部不可变身份；sourceEventId/correlationId 不能替代其唯一性。精确同正文重放幂等，不同正文复用身份必须失败关闭。
- correction/revocation 只能追加并引用同 Subject、写入历史中已经存在的目标；禁止删除、原地修改或前向引用。
- FACT、OBSERVATION、INTENTION、CORRECTION 和 REVOCATION 无论是否迟到均不得携带 mutation；新显式 StateMutation 只属于 Action Gate/Evolution 产生的 STATE_CHANGE。既有 LEGACY/interaction 兼容边界保持不变。
- Timeline 不提供 save/update/delete/overwrite；排序键固定为 occurredAt、observedAt、recordedAt、eventId，默认窗口 50、允许 20—100。
- P03 test-only Fixture 只能显式适配为 Event 候选，不能自动持久化 PlatformObservation 或伪装真实历史。
- P03 在用户验收前最多标记 `IMPLEMENTED_NOT_ACCEPTED`；用户已于 2026-08-30 正式验收并更新为 `ACCEPTED`。P04 授权仍须另行发生，不得由 P03 验收自动推导。

## 18. P04 Memory Consolidation 与 DerivedSummary 规范

- SubjectState 是当前状态权威，Event/StateUpdateRecord 是客观历史权威，Memory Store 只权威保存 Memory 记录及其证据链；Timeline 和 DerivedSummary 都是可重建派生视图。
- 正式 Memory kind 只使用 episodic、semantic、relational；正式 evidence type 只使用 experiential、analytical、external。旧兼容输入只允许在边界单向映射。
- Memory、Summary 和 lineage 必须保存在同一 MemoryRepository 权威边界内；禁止独立 Summary Store、Summary Engine 或第二 Memory Authority。
- consolidation identity 与 canonical 输入相同必须幂等，不同输入必须身份冲突。同一 root evidence 经 Event、Memory、Summary、检索、重建或重启只贡献一次；Summary 不能成为独立 Learning 证据。
- DerivedSummary 必须追溯到当前有效来源，来源变化后旧版本必须失效或被替代；固定 Fixture 和生成器下重建确定。Summary 不得创建 Event/StateMutation、推进 revision 或冒充事实、Confirmed Memory、Self-Narrative。
- correction/revocation/deletion 只通过追加式 Memory 版本和 lineage 墓碑传播；原 Event 与 Memory 历史不删除、不就地改写。P04 不提供永久删除命令。
- P04 默认 `ENGINE_PRIVATE`，没有自动过期、后台线程或 Scheduler。HOT/WARM/COLD/ARCHIVED 容量是可配置默认值，达到容量只允许显式重算和降温，不物理删除。
- P04 测试只使用临时 TEST root，不访问正式 `.continuity-data`、Vio、网络、Provider、凭据、MCP 或外部存储。该隔离不禁止 P05/P06/P16/P22 的未来授权接入。
- P04 本地实现完成时最多标记 `IMPLEMENTED_NOT_ACCEPTED`；用户已于 2026-09-01 正式验收，当前为 `ACCEPTED`。P04 验收不自动授权 P05，P05 仍须独立 Stage Brief 与用户授权。

## 19. P05 Context Router 规范

- Router 必须位于结构化 Perception 之后，只负责“打开哪些逻辑分区、向哪些来源取多少候选”；P06 才负责最终 Context Composer、Authority 分层和 token 级裁剪。
- RoutePlan、Candidate Manifest 和 Context Trace 都是可重建的只读选择/审计结果，不得成为 Store、事实权威、SubjectState、Memory 或 Thinking 输入权威。
- Retrieval Budget 与 Storage Budget、未来 Context Budget 分离；默认候选 50，可配置 30—80，并在 query 前限制每来源范围。禁止来源失败后全库扫描或扩大到未授权来源。
- 候选必须验证 subject/environment、visibility、status、version/hash/revision；保留引用前再次验证。权限未知、跨边界、失效、撤销、被替代或漂移均 fail closed。
- 排序必须结合 purpose、relevance、recency、importance、activation，并用稳定 ID/source/version 进行确定性 tie-break；相同输入、状态、配置、时钟和来源版本必须同结果。
- Context Trace 不保存原始秘密、凭据、完整敏感正文或认证材料，不得反向成为下一轮 Router、Thinking、Evolution、Memory 或 SubjectState 输入。
- P05 不创建 Event、StateMutation、Evolution、Memory、Summary，不推进 revision，不修改现有 `ThinkingProvider.think(PerceptionResult, TokenBudget)` 外部兼容接口。
- P05 施工与测试不访问 Vio、网络、真实 Provider、凭据、MCP、外部数据库或正式 `.continuity-data`；这一隔离不是长期产品禁令，P06/P16/P22 仍按阶段开放。
- 用户已于 2026-09-03 正式验收 P05/P06（D-046、D-048），于 2026-09-04 正式验收 P07/P08（D-050、D-052）；当前均 ACCEPTED。各阶段验收不自动授权下一阶段；P09 已由 D-053 单独授权，P10—P23 仍需用户独立授权，不因 P08 验收扩大方案 A、生产 exactly-once 或 Git 权限。

## 20. P06 Context Composer 与 Authority 分层规范

- Composer 只能消费 P05 `COMPLETE` Route Result 的既有 Manifest 引用，不得重新搜索、打开分区、扩大来源或改变 P05 Retrieval Budget。
- Authority 固定为 confirmed_state、confirmed_memory、derived_summary、retrieved_candidate、raw_source，并只能由可信 resolver/source binding 密封；候选自报标签和正文均不可信。
- 精确解析必须验证 subject、environment、source、stable ID、version/revision、content hash、visibility 与状态。Manifest 外材料读取、跨边界、漂移或权限变化必须失败关闭。
- Context Budget 与 Storage、P05 Retrieval、Thinking/Provider TokenBudget 分离。必须先验证和精确去重，再裁剪；受保护 identity/continuity/relationship 不得被普通预算删除。
- Summary 与 raw source 不得因文本相似合并或提升 Authority。材料冲突只能并列保留，P06 不实施 P07 矛盾检测或裁决。
- CompositionTrace 只保存引用、hash、Authority、预算、计数和原因码，不得保存完整正文、秘密、凭据或 Provider hidden Chain-of-Thought。Manifest candidate missing 与 P05 upstream notice 必须独立计数；Composer 自有 resolver 总读取数及按 source ID 分解必须进入规范 hash，required/optional 不得抹掉具体来源失败原因。
- Composer 没有 Context Store、Event、StateMutation、Evolution、Memory、Summary、Timeline、SubjectState 或 revision 写权限；所有 fragment 的 `direct_state_write_allowed` 必须为 false。
- P06 不修改生产 `ThinkingProvider` 或 E5-A；P09 才完成正式运行链接线。P06 的本地隔离不是长期禁止 Context 进入 Thinking，P09/P16/P22 仍按阶段开放。

## 21. P07 Contradiction Detector 规范

- P07 只接受 P06 `COMPLETE`、consumable 且全部 binding/hash 一致的 Context；禁止重跑 Router、重新检索或读取 Manifest 外底层材料。
- claim 必须结构化并由可信 resolver 从 fragment Authority、source/version/hash/provenance/time 密封；不得从普通正文关键词、相似度或候选自报字段猜测。
- 正式类型只覆盖 `EPISTEMIC`、`EVIDENTIAL`、`COGNITIVE`；LOVE/HATE 等 Ambivalence/Psychological Conflict 必须排除并留给 P14/P15。
- 检测不得按 recency、confidence 或 Authority 数值静默选赢家；冲突证据保留 contested/isolated disposition、verification task 与稳定 reason。
- resolution、reopen、supersession 与 referral 必须 append-only 且携带 exact source hashes；不得直接写 SubjectState、Event、Memory、Timeline、P06 snapshot 或调用生产 Evolution。
- P07 repository 是非权威、可验证的审计组件；canonical identity/body 冲突、非法 transition、断链、跨 subject/environment 与篡改必须失败关闭。
- P07 不实现 P08 Planner 或 P09 正式接线，不访问 Vio、网络、Provider、凭据、MCP、外部数据库或正式数据。
