## 修复为何成立

本轮只改变：

- `src/continuity_engine/storage/json_repository.py`：增加内部 `_retain_cleanup_error`，在清理失败时保留原主异常自然向外传播，不再在清理处理器中重新抛出主异常而覆盖隐式上下文。
- `src/continuity_engine/storage/json_runtime_repository.py`：复用同一内部处理。

显式原因和隐式上下文均保留，清理异常的原因仍可追溯；对当前覆盖场景避免因追加清理错误产生新循环。原主异常对象、类型及错误码保持，正常 traceback 可以格式化。本结论不扩展为“所有任意构造的异常图都被通用修复”。

原两条失败均验证了“原生替换拒绝 → 当前授权/版本拒绝 → 清理失败”的组合。上次为 4 PASS、2 FAIL，本次原六项 6 PASS，原探针和失败原件保留，没有改断言。

额外四项独立验证：

1. 无 P18 重试守卫的公共 SubjectState 保存，仍只替换一次，顶层仍为原生拒绝，原 errno/winerror 与文件绑定保留；附带清理原因不丢。
2. 不在 checkpoint 事务中的保存，仍不借机获得重试资格，原生拒绝没有被改成 deferred。
3. `raise ... from None` 场景保留原隐式错误的可追溯性及清理原因，顶层授权拒绝、目标字节和零更新历史保持。
4. 替换之前 fsync 就失败，再遇清理失败时，顶层仍为原 fsync 错误，替换调用为零，原目标及历史不变。
