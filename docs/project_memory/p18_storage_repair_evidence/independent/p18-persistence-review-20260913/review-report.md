## 一、这次实际验证了什么

正常读文件也可能短暂阻止 Windows 原子替换该文件。这不是“成功执行就必然成功存档”：实际效果和 TEST credits 可以已发生，而 SubjectState 仍未写入。当前实现对已识别的短时共享冲突有限等待；等待后重新检查当前 Context、控制和目标文件字节。长期占用会真实报告失败，把已经完成的事实留给后续合法恢复，而不是无休止占住宿主。

独立新增的集成反例不替换 `os.replace`、共享冲突识别器或等待器：真实打开目标读句柄，在第二次原生 Evolution guard 到达时解除句柄或发出 PAUSE/STOP。这验证了实际进入等待之后的控制行为，不只是“写入前就停止”的简单情形。

检查结果：

- 短时读句柄解除后，原生重试完成一次状态提交。
- 等待期间 STOP 阻止新的状态提交；已经发生的效果与 TEST credits 各一次，不被抹掉或重做。
- 等待期间 PAUSE 阻止提交；RESUME 后用原 ThinkSession 补存，不重复效果或扣费。
- 持续占用超过本次等待期限时，状态停在旧版本，宿主仍活着且能接受 PAUSE；解除占用、恢复后能补存。
- 同一长期占用场景重开实例后，仍保留 PAUSED；明确恢复后补存原事实，新实例 Provider 调用次数为零。
- 重试授权作用域不泄漏到另一线程；嵌套作用域异常退出后恢复外层检查器。
- 仅有 winerror5、实际没有共享冲突时，不盲目重试。此项明确使用错误注入；不冒充真实 OS 原因实验。
- 施工方原有测试覆盖撤权、字节版本改变、写入/flush/fsync/清理失败、主异常保留、已提交返回丢失与诊断兜底；本轮独立重跑全部 P18 正式测试。

这些是当前本地 Windows、TEST Fake 与既有契约下的结果，不是任意生产 Adapter 的 exactly-once 保证，也不是任意跨进程并发写的完整事务保证。
