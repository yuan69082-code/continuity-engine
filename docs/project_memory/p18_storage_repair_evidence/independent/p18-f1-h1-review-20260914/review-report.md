## 2. 必须解释清楚：真实文件失败与冻结时钟是两层条件

F1 的当前机制：

1. 实际读句柄阻止一次原子替换，OS返回winerror5。
2. 读者在错误分类探测之前关闭；当前DELETE探测成功，原分类返回False，当前提交不在原写入内部重试。
3. 原任务转入等待确认。原始运行时允许到期后查询及续接。
4. 本次受控时钟停在10:02:00 UTC，next_check_at是10:02:05 UTC。现实等待25秒并不会推进该测试时钟，因此原断言超时。

H1 的当前机制：

1. 发布资源等待checkpoint时发生真实替换失败。
2. `_tick`把该异常归入WORK_PORT_UNAVAILABLE并另写BACKOFF；短占用已解除，第二次保存成功。
3. 时钟停在09:01:00 UTC，next_check_at是09:01:05 UTC，原观察器等不到资源等待状态。

因此，当前已证明的是短读竞争后的提交/观察退避路径及其冻结时钟表现；没有由此证明正常走时的宿主必然永久死锁或停止。两次独立超时现场宿主均活着、仍为desired RUNNING，且均接受STOP退出0。

施工方定点还记录了F1将可信时间推进到查询水位后，通过原事实恢复，Provider仍两次、token仍640。这项是核对引用，不冒称本任务另行执行；它不能代替原短占用修复，但说明必须区分立即重试与到期恢复。

修复验证必须补充同样受控占用、可信时间持续推进的真实进程对照，以区分正常退避、恢复失败与仅有冻结时钟的观察失败。不能通过放宽原超时或擅自推进原反例时钟，把原FAIL改绿；新增对照应单独计数。

## 3. 对拟议公共修改的判断与条件

允许用户考虑批准的范围：

- `src/continuity_engine/storage/json_repository.py`：已有P18显式作用域中，补齐短占用在分类前已经解除时的有限、同提交重试条件。
- `src/continuity_engine/storage/json_runtime_repository.py`：P18 checkpoint接入经验证的有界处理，保留事务锁及控制/版本绑定。
- 必要的正式P18回归测试及证据/档案更新。

此范围有当前反例支持，但方案尚未实施，不能提前保证正确或没有公共影响。建议授权时同时保留以下约束：

1. “现在探测允许访问”不等于证明先前winerror5必然来自共享冲突。新分支应准确命名为当前条件允许的有限重试，不编写历史原因。
2. 不把所有PermissionError/errno13/winerror5一律变成可重试。明确目标、自建临时文件、路径与必要访问条件的核查，以及持续拒绝时的失败行为。普通权限拒绝、磁盘/路径错误、损坏和版本冲突不能被吞掉。
3. 没有显式重试授权的公共旧调用路径保留原行为。重试范围只覆盖同一已构造提交，不重新调用Provider、不重派任务、不重复扣费；本地效果为零的F1/H1反例之外，还应覆盖有实际TEST效果的恢复。
4. 保持重试等待有界、PAUSE/STOP及当前授权有效；checkpoint重试保留同一个控制事务，不嵌套争抢原非重入OS锁，不重复增加revision，不覆盖新的control/generation/owner。查询与控制竞争需要实际进程验证。
5. 保留目标原字节/版本检查；同时核查待提交临时内容身份。当前SubjectState只有本地RLock及重试前字节比较，不能把它冒称为任意跨进程原子CAS事务保证。
6. 除批准两文件外，如果必须改公共Scheduler、C1、Thinking、权限或计费语义，须再次报告并等用户确认。

一项需透明处理的旧独立检查：上一轮规划侧八项检查中含 `test_winerror5_without_actual_handle_conflict_is_not_retried`，它在当前可访问文件上注入固定winerror5，要求一次拒绝、不进入guard。新“占用已解除”分类可能触及这一行为假设。施工方必须复跑并解释结果；不能静默删除或改写规划侧探针，也不能一边改变这种行为、一边声称所有已验证拒绝行为完全未变。若需要调整该行为约束，列出原因、真实权限拒绝对照和影响，由用户明确决定；不要用伪造的永久拒绝来证明历史共享冲突。
